# launchpad-app-to-video

This skill adds the Launchpad-specific front end to HyperFrames. Once step 0 passes, load the `hyperframes` skill (`/hyperframes:hyperframes` in Claude Code) and follow its contract.

## Third-party tools
The video is built with tools from other vendors. The user installs them; this skill bundles none of them, and the user is responsible for the licence of any media they add.
- **HyperFrames** (Apache-2.0, by HeyGen, not affiliated with Pega): HTML-to-video skills and CLI. Required.
- **Node.js 22+, FFmpeg, Chrome**: used by the HyperFrames CLI to render. Required.
- **HeyGen account** (optional): music catalog, subject to HeyGen's terms and the user's plan.
- **Kokoro-82M** (Apache-2.0, optional): local, offline voiceover.

## How a run goes (the user types as little as possible)
The user may only say "/launchpad-app-to-video" or "make a teaser for <app>". Do not ask them to run separate setup prompts. You drive the whole run and stop only at these gates: (a) setup items that need their own terminal or sign-in, (b) the one question round, (c) a preview build OK, (d) picking a storyline, (e) Studio preview approval. Between gates, keep going without asking "shall I continue?". If the app name was not given, ask for it inside the step 2 question round only if step 0 passes without it; otherwise ask it alone as the first message. When the user returns after a setup action ("done", "signed in"), re-run the failed checks yourself and carry straight on.

## 0. Prerequisites (check these first, before any other step)
Run all the checks yourself, in one pass, without asking first. Reply with ONE checklist (a line per item: OK / missing). Fix what you can. For everything that needs the user, give a single numbered "Do this once" list in the order to do it, each step with its exact copy-paste command in its own code block and where to run it (the assistant's own settings or command line for plugin, skill and MCP steps, e.g. an interactive `claude` terminal for `/plugin` and `/mcp` in Claude Code; a normal terminal for `npx`, `nvm` and package managers), then tell them to reply "done" and to restart the session if you listed a plugin install. Skip everything already OK, and if all required items pass say "Setup OK" in one line and go straight to step 1. Ask before installing anything on their machine. Do not continue to step 1 until the required items pass. Items 3, 4 and 5 are optional: list them once as "optional, say 'skip' to go without" and never block on them.

**Required**
1. **Launchpad MCP.** The Launchpad authoring MCP server, under whatever name the user configured (`launchpad` by default; a project may define its own in a config file such as `.mcp.json`). Check: its tools (`find_application`, `list_rules`, `get_rule`, `search_rules`) are available (load them first if your assistant defers tools), then call `find_application` with the app name. Fix:
   - Server configured but tools missing, or "needs you to sign in again": the user approves the server and signs in through the assistant's MCP settings (Claude Code: `/mcp` in an interactive `claude` terminal; the desktop Code tab cannot open that dialog), then restarts or retries. Never ask for codes, tokens or callback URLs.
   - No Launchpad server configured, or another Launchpad environment: follow the `launchpad-byoa-mcp-initial-setup` skill (older installs: `launchpad-byoa-mcp`), or point the user to it: https://github.com/pegasystems/pega-launchpad-agent-skills/blob/master/skills/launchpad-byoa-mcp-initial-setup/SKILL.md. It needs the Launchpad application URL and an OAuth Client ID the user creates in that environment (Administrator Setup > OAuth 2.0 client registrations > Add: Public client, MCP Client, Authorization Code, PKCE). Never request a client secret.
   - Connected but the app is not found: ask for the exact app name; the MCP user may lack access.
2. **HyperFrames.** All three must pass:
   - Skills: `hyperframes` (and `hyperframes-cli`, `media-use`) are in the skill list (in Claude Code they show as `hyperframes:hyperframes` and so on). If not, install them and restart the session:
     - Claude Code, in an interactive `claude` terminal: `/plugin marketplace add heygen-com/hyperframes` then `/plugin install hyperframes@hyperframes` (installed copy in `~/.claude/plugins/cache/hyperframes/`).
     - Other assistants (Copilot, Cursor, Codex, Kiro, OpenCode, ...), in a terminal in the project: `npx hyperframes skills update` (installs the core set: `hyperframes`, `hyperframes-cli`, `hyperframes-registry`, `media-use`). See https://github.com/heygen-com/hyperframes for the current install options.
   - Node >= 22: `node -v`. The default shell is often older. With nvm, look for one with `ls ~/.nvm/versions/node`; if a 22+ exists, prefix every HyperFrames command with `PATH="$HOME/.nvm/versions/node/<v22+>/bin:$PATH"` (the examples below use this prefix; drop it when the default `node` is already 22+). If none, the user runs `nvm install 22` or installs Node 22+ from nodejs.org.
   - CLI and render tools: `npx --yes hyperframes@<version> doctor` (use the installed skills' version, e.g. 0.9.6, everywhere). It must show Node, FFmpeg/FFprobe and Chrome as OK; if FFmpeg is missing the user installs it (macOS: `brew install ffmpeg`; Linux: the distro package, e.g. `sudo apt install ffmpeg`; Windows: `winget install ffmpeg`); Chrome is fetched by HyperFrames on first render. Docker, whisper and Kokoro are optional; ignore their failures. Ignore MusicGen and Lyria too: this skill never uses them (see Rules, licensed media).

**Needed later (check now, ask in the question round)**
3. **Music (optional, strongly recommended).** `npx hyperframes auth status` should say signed in, and the `heygen` CLI should be on PATH (`which heygen`). If not: the user runs `PATH="$HOME/.nvm/versions/node/<v22+>/bin:$PATH" npx --yes hyperframes@<version> auth login` (Node 22, finish the browser step) and installs the HeyGen CLI from https://developers.heygen.com/cli. Without these the film ships with bundled SFX only (or silent), or with a music file the user supplies and holds a licence for. A teaser is commercial use: HeyGen's terms limit free-plan output to personal, non-commercial use, so the user confirms their HeyGen plan and licence cover a marketing video before catalog music goes in.
4. **A way to see the app.** Any browser tool the assistant has (for example a built-in browser pane, Claude in Chrome, Control Chrome, Playwright, or an editor's integrated browser) plus the user's willingness to sign in to the Launchpad preview manually; or the user can upload screenshots instead (see step 2). Claude in Chrome needs its extension installed and signed in: https://chromewebstore.google.com/detail/fcoeoabgfenejglbffodgkkbkcdhcgfn

5. **Voiceover (optional, off by default).** Local Kokoro TTS via `npx hyperframes tts`. Check: the `TTS (Kokoro)` line of `doctor` says installed, run with `HYPERFRAMES_PYTHON` pointing at a Python 3.10-3.13 venv that has `kokoro-onnx soundfile` (on macOS, `/usr/bin/python3` is 3.9: too old). Install steps, voices, script, generation and mixing: `references/voiceover.md`. Missing Kokoro never blocks a run: the film is type-led and works without a voice.

Record the result in `projects/<app>/app-brief.md` under "Environment" (versions, what was missing, what the user fixed) so the next run can skip what already passed.

## 1. Discover the app
- Connect via the Launchpad MCP. `find_application`, then `list_rules` / `get_rule` for: CaseTypes (stages, processes), Personas/AccessGroups, DataTypes, Agents/GenAIConnect, Integrations, Portal, Theme (colours, logo, fonts).
- Write `projects/<app>/app-brief.md`: facts only, each with the rule name/ID it came from. Include real UI labels.
- Add an **Enterprise value** section to `app-brief.md`. Launchpad apps are sold to enterprises, so list the evidence for each pillar, with its source. Write "none found" where there is none, and never fill a gap with a guess:
  - **Cost:** manual work the app removes: automations, decisions and straight-through steps that replace hand-offs, SLAs, work queues and routing, prefilled or extracted fields, fewer systems to touch (integrations).
  - **Security / control:** personas and access roles, access policies (record-level), approval steps, audit trail or history views, authentication profiles, data that stays in the case.
  - **Scale:** the provider/subscriber model and Configuration Sets (one app serving many customers), work queues, bulk actions, integrations, data pages.
  - **Predictable AI** (only if the app has Agents or GenAIConnect): for each AI feature, write down what goes in (the case fields or attachments it reads), what comes out (the typed fields it fills, the structured response), the tools it is limited to, and the human step that reviews or approves its output. Write "AI suggests, human decides" only if a rule shows an assignment or approval after the AI step. Also search for automations that set the decision field themselves (e.g. an "Auto Approve" that sets `EvidenceSufficient = true`), and check where they are called: if they can skip the human step, the claim is false until shown otherwise. If the AI's input is hard-coded demo wiring, a captured AI result is demo data: label it so.
  - **Platform facts** (true of every Launchpad app, from the `launchpad-overview` skill, which the Launchpad MCP server provides; if it is not installed, ask the user for these facts or leave the platform line out): multi-tenant SaaS, managed scaling, role- and attribute-based access, and the platform's compliance posture (SOC 2, ISO 27001, GDPR, HIPAA). Mark them "platform", word them as "Built on Pega Launchpad", and confirm with the user before any compliance line goes on screen. Word it precisely: SOC 2 and ISO 27001 are audited certifications; GDPR and HIPAA are laws with no official certification, so say "supports GDPR and HIPAA compliance", never "GDPR certified" or "HIPAA certified". Use the user's current wording from Pega's trust documentation when they have it.

## 2. Ask the user (one round, max ~5)
Only what the app cannot answer. Combine these into five questions or fewer:
1. Who is the viewer (role, industry), and what is the pain or old way?
2. **The opening outcome.** Draft 2-3 opening lines from the brief (see step 3, "Open on the outcome") and ask the user to pick one or edit it. Ask what proof they can stand behind: a customer number, a pilot result. No numbers go on screen without it.
3. Which enterprise pillar does this buyer care about most (cost, security/control, scale, predictable AI)? Default: the pillar with the strongest evidence in the brief.
4. The differentiator: what this product does that the alternatives (spreadsheets, email, a legacy tool, a competitor, a generic AI chatbot) do not, and the ONE thing to remember.
5. CTA, tone, music, and voiceover: none (default) or a Kokoro voice (offer 2-3 from `references/voiceover.md` and whether you write the script or they supply it).

State defaults for the rest. Append answers to `app-brief.md`.

Also ask for sound, in this round, not at render time. Offer: (a) HeyGen catalog music, which needs the user's one-time sign-in and CLI install (see Gotchas) and a HeyGen plan whose licence covers commercial use; (b) a music file the user supplies and holds a licence for; (c) bundled SFX only. Never generate music with MusicGen or Lyria (see Rules).

For screenshots, name the key screen(s) and explicitly ask which source to use. Offer these options in preference order:
1. **App preview or subscriber link:** when a preview is needed, request one by calling the Launchpad MCP build tool (the tool that builds the app/branch and returns a Preview URL; find it in the MCP tool list) for the app and branch found in step 1. Building can take a while; wait for it to finish and use the URL it returns. If the build fails or returns no URL, report the reason and ask the user for an existing preview or subscriber link. Never construct a URL from an app ID, namespace, or guessed domain. Open it in the browser, let the user sign in manually, confirm the target screen, then capture it. Never ask for or handle credentials. Use whatever browser tool is available (e.g. Control Chrome, Claude in Chrome, the editor's integrated browser, or Playwright) to read the page, navigate to the requested screen, and take screenshots; prefer a real signed-in browser session so the user's manual login is reused.
2. **User-supplied screenshots or recordings:** ask them to upload the screens or clips they want featured. Ask for a short screen recording (10-30 s, 1920x1080 or larger, one action per clip: open the case, fill the field, approve) for the proof beat whenever they can: real UI in motion makes the demo dynamic in a way stills cannot. Stills are fine for everything else, at full size (about 1400 px wide or more).
3. **Adapted generic Launchpad screenshots:** only with the user's approval, adapt existing generic Launchpad captures to illustrate the app's use case. Label these frames as illustrative, not authentic app UI; do not invent metrics, records, or capabilities.
The user may choose a different source for different screens. If the preferred source is unavailable, ask before falling back. Do not capture or retain sensitive data; have the user navigate to a safe example before capture.

A build only compiles the current branch for Preview; it does not change rules. Subscriber URLs are different: they come from manual subscription provisioning by a Provider Administrator (see Subscriber Onboarding and Go-Live in the `launchpad-general` skill, provided by the Launchpad MCP server). Do not provision a Subscriber, create a subscription, publish, or change DNS to obtain screenshots.

## 3. Story
Follow HyperFrames `story.md`: three different storylines in words → `STORYLINES.md` → recommend one → user picks. Beats: **outcome hook**, tension, reveal, proof (3-6 verbs in real UI), **enterprise proof**, payoff, claim, end card. 30-60 s, 1920x1080, 30 fps. This is a marketing film for an enterprise buyer: it sells an outcome and shows why this product is the safe choice, not a feature tour.

**Open on the outcome (0-3 s).** The first frame is a benefit statement or question in large type, about what the viewer gets, not what the app is. No logo, app name or feature name in the hook. Use one of these patterns:
- Question: "Want faster and more accurate audits?"
- Imagine, joining two goals that usually trade off: "Imagine improving customer satisfaction WHILE reducing your costs." Set the joining word (WHILE, AND, WITHOUT) in a different weight or colour so it reads as the twist.
- What if: "What if every claim was triaged before you opened it?"
- Pain flip: "Still chasing approvals by email?"
Rules: at most about 10 words. Written in the viewer's words, about their outcome (speed, accuracy, cost, risk, customer satisfaction). It must read on mute. No number unless the user supplied it. The payoff and claim must answer the hook (the question asks "faster and more accurate audits?", the claim answers "Audits, done right the first time."). Each storyline in `STORYLINES.md` starts with its hook line written out.

**Voiceover (only if the user asked for one).** Write the script per beat with the storyline (about 2.3-2.6 words/s, silence around the hook and end card) and let the user approve the words when they pick the storyline. The voice adds the sentence a headline compresses; it never replaces on-screen type, and every spoken claim follows the same sourcing rules. Details: `references/voiceover.md`.

**Enterprise proof (one beat, 4-8 s).** After the product proof, show the one or two pillars from step 2 that matter most to this buyer, each as a short line on a real screen or element that supports it. Examples: the stage bar or SLA for cost or speed; a persona-routed approval step or access-restricted view for control; work queues or the subscriber model for scale. Each line traces to the "Enterprise value" section of the brief. A pillar with "none found" stays out of the film. "Built on Pega Launchpad" platform facts may close this beat as one line, never as the main claim.

**AI, shown as predictable (only if the brief has AI evidence).** Enterprises buy AI they can control. Show the AI as one step in a defined process: the input it reads → the structured, typed result it fills in on the real screen → the person who reviews or approves it. Good lines: "AI drafts. Your team approves." "Same inputs, same checks, every case." "Every AI step on the record." Use a line only if the brief shows that wiring (structured output fields, limited tools, a review/approval assignment, history). Never "autonomous", "magic", "replaces your team", or accuracy rates the user did not supply. If the app has no AI, say nothing about AI.

**Differentiate.** Label the tension beat as the problem, on screen (a line such as "Today's audit headache:" or "Today:" above it, or a contrasting ground), or viewers read the old way as something the product does. Name the alternative the viewer uses today (from step 2) in the tension beat, and show in the proof what this product does that the alternative cannot. The claim says the differentiator in one line, not a generic "work smarter".

## Make the demo dynamic (and fill the frame)
The strongest teasers keep the product moving and leave no empty space on screen. Both come down to measurable rules, written into `SPEC.md` per shot and checked in review. The UI on screen stays real: motion comes from the camera, the crop and the cut, never from drawing UI the app does not have.

**Dynamic: the product is always moving or about to.**
- Shot length: average 1.8-3 s in the proof beat; nothing static for more than 3 s (`check` flags `dead_stretch`). A demo that holds one framing for longer (up to 7-10 s) only while the UI itself acts (a recording, a value filling in, a stage advancing).
- Every real-screen shot has one camera move: a push-in from the full panel to the element that matters (1.0 → 1.15-1.6x over the shot), a track across a table or stage bar, or a zoom through a button into the next screen (HyperFrames `motion.md`). Vary the move from shot to shot; never the same push twice in a row.
- Show the verb happening, in order of preference: (1) a real screen recording of the action; (2) a before/after pair of real screens cut on the beat (empty field → filled field, "In progress" → "Resolved"); (3) a lift: crop the real element from the screenshot (a status chip, the AI result field, the approve button), scale it up 1.1-1.3x with a soft shadow, and set it back. Never fake a cursor, a typed value, a click result or a state the captures do not show.
- Speed contrast: fast cuts (0.4-0.8 s) in the tension beat and on the proof verbs, one longer hold (2-3 s) on the payoff and the claim. Arrivals on long eases (`expo.out`), camera moves `power2.inOut`; never `power2.out` 0.5 s on everything.
- Kinetic type works with the UI, not after it: the verb ("Assigned.", "Scored.", "Approved.") lands on the same beat as the element it names, 3-7 words, large, then holds still while the camera keeps moving.
- Polish = confident and crisp, not effects: one strong brand colour on the key element, tight type tracking, clean seams on the beat, sound hits on the cuts. Still banned: glow, particles, glass, purple gradients, everything fading up.

**Fill the frame: no empty space.**
- The hero of every shot fills at least 40% of the frame height or width; a real-UI shot fills at least 60%. Crop the screenshot to the panel, table or card that proves the line, and push in; never place a whole small screenshot in the middle of a plain ground.
- No dead margins: any empty area over about 15% of the frame gets a job, filled with the headline or verb, a second real crop (the detail beside the overview), the stage bar, or the brand colour field bleeding off the edge. Empty space is a choice, not a leftover: allowed only around the hook line and the end card, and then the type is at least 8-9% of the frame height.
- Layouts that fill: full-bleed UI with type over a brand-colour band; a 60/40 split (real screen left or right, big type on the other side, both running to the edges); a tight crop that bleeds off one or two edges; a real UI element blown up to full frame behind the headline. Not three cards in a row, not a centered floating window.
- Low-resolution captures are the usual cause of small, floating UI. Ask for full-size screenshots or recordings early (step 2); if one stays soft, crop tighter and move faster rather than shrinking it.
- Placeholders fill the frame too: a full-bleed labelled PLACEHOLDER panel at the size the real screen will take, so the layout is already right when the capture arrives.

## 4. Spec, build, review
`SPEC.md` with numbers (look from the Theme rule; per shot: duration, camera move with start/end scale, hero fill %, and what fills the rest of the frame; a voiceover table with beat, start, end, line, voice, speed, or "Voiceover: none") → build in `projects/<app>/` → `npx hyperframes check --json` → `snapshot --review` → `REVIEW.md` (also check: no shot static for more than 3 s; every real-screen shot has a camera move and fills at least 60% of the frame; no empty area over about 15% outside the hook and end card; the hook is an outcome, not a feature; the claim answers the hook; each enterprise and AI line has its source in the brief; with a voiceover, each line fits its beat, the music ducks under it, and the film still reads on mute) → open Studio preview → render only after approval.

## Gotchas (learned)
- HyperFrames needs Node >= 22 (see step 0): run it with a Node 22+ on PATH (with nvm: `~/.nvm/versions/node/<v22+>/bin`). The user's own terminal commands (auth login, installs) need the same prefix, or they fail with "requires Node.js >= 22".
- Verify every claim against rule bodies, not the app description (an automation can be an empty stub; a feature can have no rule). Check demo wiring (hard-coded URLs, constant values) before presenting a feature as real.
- Runtime UI is behind sign-in: name each needed screen and ask which screenshot source to use. Prefer browser capture after the user signs in manually, using the Preview URL from the MCP build tool or an existing subscriber link; otherwise use user-supplied images or, with approval, adapted generic Launchpad captures. Mark placeholders as PLACEHOLDER and any adapted/mock screen or invented example data as Illustrative.
- Preview URL: the Launchpad MCP `build` tool (needs the user's explicit OK per build) returns `previewURL` and `newPreviewGatewayUrl`. Open the `newPreviewGatewayUrl` (`.../preview-jobs/<id>`) in the browser; the bare `previewURL` returns a 400. It redirects to the Pega sign-in: the user signs in manually. The app runs in an iframe inside a preview shell, so page-reading tools (accessibility tree, page text) cannot see inside it; drive it with coordinate clicks (screenshots can lag one call, so wait ~2 s before looking).
- Capture size: the built-in browser pane returns screenshots at about 800 px wide even with a 1920x1080 emulated viewport, too soft for 1080p panels. Widen the pane first or find a full-resolution capture route; screencapture is blocked and Claude in Chrome may be disconnected. In practice the user's own full-size screenshots (about 1400-1500 px wide) were the working route: ask for them early, one per named screen.
- Using supplied screenshots: crop to one card/panel/table per scene (PIL `Image.crop`; run plain `python3`, not `-I`, to get PIL). Paint over tooltips and cursors with sampled neighbouring pixels. Show no personal names (use tables/charts without owner columns, or crop them out). Scale 1.3-3.6x is soft; push-ins (GSAP `scale/x/y` on an `<img>` with `transform-origin: 0 0`, `data-layout-allow-overflow`) hide it better than static full-width panels. Never edit the numbers or text in a screenshot.
- Screens must agree: do not put two screens on one film if their data contradicts (an Audit Agent answer about a different audit than the case shown) or if they come from different environments/themes. Drop the odd one out.
- Theme: screenshots from the user's environment may use a different theme than the Theme rule on `main` (one app had teal in the rule and gold in the user's screens). Take the video palette from the screens that will be shown, and say so in the reply.
- Headline words are claims. Pick words the real screens support (the stage bar shows progress, so AUDIT-READY is OK as a headline; do not fake completed stages, scores or green chips). An empty feature panel (AI fields showing "No" / "--") shows the feature exists, not a result: say so in REVIEW.md and ask for a populated capture.
- Theme rule gives palette, font, logo name. Brand font may not be bundled and a download needs the user's OK; the logo must be exported from the app.
- Scene seams: wipe the scene `#root` with clip-path (hosts start 0.4 s early, higher z-index), not only a ground layer. Use the same units at both ends (`inset(0% 0% 0% 100%)` → `inset(0% 0% 0% 0%)`): with a bare `0` end value GSAP does not interpolate, the scene stays hidden for 0.4 s and then pops in on the bar (every seam of an early test film was a hard cut because of this). Verify with `snapshot --at` inside the overlap, not only the seam sheet.
- Sound: put the cuts on a beat grid (bar = 240/BPM s) from the start. Offline SFX are bundled (`media-use/audio/assets/sfx`, Pixabay Content License: free for commercial use inside a film, but the raw files must not be redistributed on their own, so never publish a project's `assets/audio/` folder; copy into `assets/audio/` with CREDITS.md): a `whoosh` per scene wipe (start = host `data-start` + 0.04, the file peaks about 0.16 s in) and one `impact-bass-1` at the claim; every `<audio>` needs an `id`, `class="clip"`, `data-start`, `data-duration`, `data-volume`.
- Music needs a HeyGen sign-in: the user runs `PATH="$HOME/.nvm/versions/node/<v22+>/bin:$PATH" npx --yes hyperframes@<pinned> auth login` themselves (Node 22, finish the browser step; `auth status` should say signed in) and installs the `heygen` CLI from developers.heygen.com/cli. Then `npx hyperframes media-use resolve --type bgm --provider heygen --intent "<feel, no tempo promises>" --project .` (force `heygen`: without it, media-use can fall back to Lyria or MusicGen, see Rules) returns `.media/audio/bgm/bgm_001.wav` (the catalog ignores the tempo you ask for: this one came back 120 BPM / 30 s). Fit it with ffmpeg: `atempo` (film BPM / track BPM) so bars match the cuts, trim and repeat whole bars, 20 ms `acrossfade` at joins, `afade` out under the end card, `apad`/`atrim` to the film length. Add `<audio id="music-bed" data-timeline-role="music" data-volume=...>`, render, then measure with `npx hyperframes audio <mp4> --json` and aim for about -16 to -14 LUFS with true peak <= -1 dBTP (bed 0.65, SFX 0.6-0.7 worked). Say it was measured, not heard. Write the track's provider and ID (from the `.media` manifest) into `assets/audio/CREDITS.md`. With no sign-in: use a licensed file the user supplies (`resolve --type bgm --from <file>`), or deliver SFX-only or silent, and say so.
- Voiceover (optional): generate one Kokoro file per line with `HYPERFRAMES_PYTHON=~/.venvs/kokoro/bin/python npx hyperframes tts "<line>" --voice <id> -o assets/audio/vo/vo-NN.wav --json`, take `durationSeconds` into SPEC.md, place each as `<audio data-audio-group="voiceover" data-timeline-role="voiceover">`, duck the music to about 0.3-0.4 under it. The first call downloads about 340 MB of model files (ask first). Shorten words before changing `--speed` (keep 0.9-1.15). Full recipe: `references/voiceover.md`.
- `npx --yes hyperframes@<pinned>` keeps CLI versions equal across steps; unpinned `npx` pulls a newer version and prompts.
- Gate before render: Studio preview (`preview --background`) and the user's approval. Render with `npx hyperframes render --quality delivery -o renders/<app>-teaser-vN.mp4 --quiet` (about a minute for 37 s), name each version, verify with `ffprobe` (video + audio streams, 1920x1080, 30 fps) and a contact sheet, then `preview --stop`. Studio may drop its own `video_<date>.mp4` into `renders/`: mention it, do not delete it.
- Keep reusing the scene structure: a hero word, one real-screen frame, a clip-path seam. Replacing placeholders with screenshots only touched the scene HTML and the audio tags; `index.html` timing stayed.

## Rules
- Prefer real UI. Missing screens are labelled placeholders and reported to the user. Adapted generic Launchpad screens are allowed only when the user chooses that source, and must be visibly labelled Illustrative rather than presented as authentic app captures.
- No invented metrics or claims; every on-screen fact traces to the app or the user.
- Dynamic and full: every shot moves (camera, cut or real UI action) and fills the frame; no small screen floating in empty space. Motion never invents UI.
- Must read on mute, with or without a voiceover. A voiceover is optional (Kokoro, user's choice) and never required. First frame is never black or a logo alone: it is the outcome hook (a benefit statement or question).
- Sell to the enterprise buyer: outcome first, then why it is safe to buy (cost, control, scale). AI is shown as a controlled, reviewable step, never as magic.
- Licensed media only. Every audio, font and image file in the film has a licence that allows commercial use, recorded in `assets/audio/CREDITS.md` (or a CREDITS.md next to the asset). Never generate music with MusicGen (`facebook/musicgen-small`, weights licensed CC-BY-NC 4.0, non-commercial) or Lyria (Google API terms not reviewed for this use), even when media-use offers them as a fallback. HeyGen catalog music only on a plan that covers commercial use. Never publish raw SFX or music files apart from the rendered film.
